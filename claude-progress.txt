  The header write and the access-log emit both sit after `await call_next(request)`
  inside the same try; only request_id_var.reset is in the finally. An unhandled
  exception runs neither, so a 500 returns no X-Request-ID and emits no access line.
  E15-S1-AC4 requires the response to echo the id, and the 500 path is the one case an
  operator needs it. No test covers it (test_log_redaction.py asserts the header only on
  the 200 path).
  NOT fixed here deliberately — it is a design decision on the platform substrate every
  later story inherits, and it is entangled with the contract drift below:
    (a) swallow the exception in the middleware and return our own 500 (we can stamp the
        header, but TestClient raise_server_exceptions semantics change and errors stop
        propagating to any outer handler), versus
    (b) log + re-raise (access line covered, header still impossible from here, because
        ServerErrorMiddleware is OUTSIDE our middleware and builds that 500 itself).
    An app.exception_handler(Exception) does not rescue option (b): Starlette binds an
    Exception-keyed handler to ServerErrorMiddleware, i.e. outside our middleware, where
    request_id_var has already been reset.
  Whoever resolves this must also pick the 500 body, which runs into the drift below.
