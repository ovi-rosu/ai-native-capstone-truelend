## User Story
As a customer, I want to see my repayment schedule and current standing and pay from the same screen so that I can stay current without contacting the bank.

## Business Value
Gives borrowers a self-service repayment surface, which is what makes the no-notifications constraint workable.

## Description
The FR-12 customer loan view: every installment with due date and amount, the current outstanding principal, the current delinquency bucket, and a repayment action whose effect is visible on reload. This is the Repay screen NFR-10 holds to WCAG 2.1 AA.

## Scope
**In:** Installment list with due date and amount per row; Current outstanding principal and delinquency bucket display; Repayment posting action from the loan view
**Out:** must not offer an early settlement, foreclosure or prepayment quote; must not expose another customer's loan; must not compute outstanding principal client-side

## Acceptance Criteria
- **E13-S1-AC1** — *Given* a disbursed loan belonging to the signed-in customer, *when* its loan view is opened, *then* every installment is listed with its due date and amount.
- **E13-S1-AC2** — *Given* that same loan view, *when* it renders, *then* the current outstanding principal and the current delinquency bucket are both shown.
- **E13-S1-AC3** — *Given* a repayment posted from the loan view, *when* the page is reloaded, *then* the displayed outstanding principal reflects that posting.
- **E13-S1-AC4** — *Given* the loan view for a delinquent loan, *when* it renders, *then* it offers no early settlement, foreclosure or prepayment quote.

### Operations
1. Add `getLoan(loanId)` and `postRepayment(loanId, amount)` functions to `frontend/src/api/loans.ts` (new), calling the shared HTTP client from `frontend/src/api/client.ts` (owned by E1-S1) against `GET /loans/{loan_id}` and `POST /loans/{loan_id}/repayments` (served by the repayment service owned by E11-S2), sending and receiving amounts only as the quoted 2dp wire string — never converting to a JS number.
2. Define `BucketBadge` in `frontend/src/ui/components/BucketBadge.tsx` (new): a presentational component rendering the loan's `delinquency_bucket` wire value as a labeled badge, with no business logic and no client-side classification.
3. Define the `Repay` screen in `frontend/src/ui/pages/Repay.tsx` (new): fetch the signed-in customer's loan via `getLoan`, render every `Installment` row with its due date and amount using `MoneyText` (owned by E9-S1, `frontend/src/ui/components/MoneyText.tsx`) over `Money.fromWire` (owned by E9-S1, `frontend/src/types/money.ts`), render the current `outstanding_principal` via `MoneyText` and the current bucket via `BucketBadge` — both taken verbatim from the server response and never recomputed client-side — and expose a repayment posting action that calls `postRepayment` and reloads the loan view afterward so the displayed outstanding principal reflects the post; render no early settlement, foreclosure or prepayment quote affordance anywhere on the screen (SG-10).
4. Add one route entry for `Repay` to the frontend route registry `frontend/src/ui/routes.tsx` (owned by E1-S1).
5. Append one screen row for `Repay` to the customer-facing screen registry `frontend/tests/a11y/registry.ts` (owned by E17-S1) so the screen is covered by the accessibility harness before it lands.
6. Append one endpoint row for `GET /loans/{loan_id}` to the read-heavy endpoint registry `backend/tests/slo/registry.py` (owned by E15-S3) so the loan read surface meets the SLO budget.
7. Add unit tests in `frontend/tests/unit/Repay.test.tsx` (new) covering AC1-AC4: every installment lists its due date and amount (AC1), outstanding principal and bucket both render (AC2), a posted repayment's effect is visible after reload (AC3), and no early-settlement, foreclosure or prepayment-quote affordance is offered (AC4).
