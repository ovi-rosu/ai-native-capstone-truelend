## User Story
As a product owner, I want a thin slice from application submission through a returned decision so that the M2 done-when is demoable before intake, scoring and underwriting go deep.

## Business Value
Establishes the submit-score-decide seam early, so the three M2 epics add depth behind a working flow rather than integrating late.

## Description
The D8 tracer bullet for M2. A customer submits against a chosen product, the application is persisted in SUBMITTED state pinned to that product's current policy version per D6, a score is returned, and a decision of AUTO_APPROVE, AUTO_REJECT or MANUAL_REVIEW comes back with at least one reason code.

## Scope
**In:** Application aggregate and submit endpoint; Submission-time policy_version_id pinning; Shallow score and decision response
**Out:** must not implement the full document checklist — that is E4-S2; must not call an external credit bureau or payment rail; must not accept a co-applicant or guarantor on the application

## Acceptance Criteria
- **E4-S1-AC1** — *Given* a chosen product and a CUSTOMER session, *when* an application is submitted, *then* a persisted application in SUBMITTED state is returned carrying the product's current policy version id.
- **E4-S1-AC2** — *Given* that application's age, income and credit-history flags, *when* the scoring stub is called for it, *then* a numeric credit score is returned and stored against the application.
- **E4-S1-AC3** — *Given* the scored application, *when* it is decided, *then* the response carries one of AUTO_APPROVE, AUTO_REJECT or MANUAL_REVIEW together with at least one reason code.

### Operations
1. Define `Applicant`, `ApplicationSubmission`, `LoanApplication` and `ApplicationDocument` Pydantic models in `backend/src/types/origination.py` (new), per `specs/design/program-design.md`'s Types section — `ApplicationDocument` is declared here (typed, empty at this tracer stage) so `LoanApplication`'s response shape is stable before E4-S2 populates it. Import `ApplicationStatus` and `DocumentVerificationStatus` from `backend/src/types/enums.py` (owned by E1-S1) and `Money` from `backend/src/types/money.py` (owned by E9-S1, already implemented).
2. Add migration `backend/migrations/versions/0005_application.py` (new) creating the `application` table per `specs/design/data-models.md` (`id`, `product_code` FK, `policy_version_id` FK NOT NULL never updated, `applicant_user_id` FK, `status`, `requested_amount NUMERIC(14,2)`, `requested_tenure_months`, applicant fields inlined, `credit_score`, `submitted_at`) with indexes `(status)`, `(product_code)`, `(applicant_user_id)`, `(policy_version_id)`; append the `Application` table class as one row to the SQLAlchemy table registry in `backend/src/repository/models.py` (owned by E1-S1; single-row registry append).
3. Define `ApplicationRepository` in `backend/src/repository/origination/application_repository.py` (new) with `insert(submission, policy_version_id, applicant_user_id)`, `get(application_id)`, `list(status=None, product_code=None, applicant_user_id=None)`, `set_status(application_id, status)` and `set_credit_score(application_id, score)`, over the `application` table from step 2.
4. Define `submit(submission: ApplicationSubmission, actor: User) -> LoanApplication` in `backend/src/service/origination/intake.py` (new): resolve the product's rules via `policy.active_policy_version(product_code)` from `backend/src/service/policy/policy_accessor.py` (owned by E2-S1, the only permitted call site per D-D); persist via `ApplicationRepository.insert(...)` pinning `policy_version_id` with `status=SUBMITTED`; set `document_checklist=[]` (full generation is E4-S2's scope).
5. In the same `intake.py`, add a deterministic scoring stub function (age/income/credit-history flags in, numeric score out — no I/O, no clock) and persist it via `ApplicationRepository.set_credit_score` (AC2); add a shallow tracer decision function mapping the score against the pinned rules to one of `AUTO_APPROVE`/`AUTO_REJECT`/`MANUAL_REVIEW` plus at least one reason code drawn from `rules.reason_codes` (AC3) — a temporary stand-in for the E5-S1/E5-S2 services, held in-memory only (no `decision_record` table exists yet).
6. Define `POST /applications` under `require_roles(CUSTOMER)` (imported from `backend/src/api/authz.py`, owned by E1-S2) in `backend/src/api/origination/routes.py` (new), calling `intake.submit` and returning `201` with `{application, credit_score, decision, document_checklist}` per `specs/design/api-contracts.md`. **First statement in the handler body, before any call that could log:** `register_sensitive(submission.applicant.pan, submission.applicant.aadhaar, <salary-document content>)` imported from `backend/src/config/logging.py` (owned by E15-S1, existing). This is the story that carries the first applicant PII, and redaction is registration-driven — `RedactionFilter` scrubs only values a caller has registered, so without this call E15-S1-AC1 is satisfied by its own test fixture while production logs the raw PAN. `backend/tests/unit/test_log_redaction.py::test_modules_handling_applicant_pii_enter_a_redaction_scope` fails any `src/` module naming pan/aadhaar/salary_doc that does not enter a redaction scope, so omitting this blocks the commit.
7. Append `app.include_router(origination_router)` to the app factory router registry in `backend/src/api/app.py` (owned by E15-S1; single-row registry append), so `create_app()` wires the origination router alongside the platform router.
8. AC1-AC3 verification: this tracer owns no dedicated test file — coverage for the submit→score→decide path lands in E4-S2's `backend/tests/integration/test_intake_pinning.py` (owned by E4-S2), which exercises this story's endpoint end to end alongside the checklist assertions it adds, covering AC1-AC3.
