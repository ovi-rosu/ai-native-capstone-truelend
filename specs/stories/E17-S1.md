## User Story
As a customer relying on assistive technology, I want every customer-facing screen held to WCAG 2.1 AA as it is built so that conformance is never a late remediation pass over three finished screens.

## Business Value
Makes an accessibility regression attributable to the story that caused it, and removes the retrofit risk of remediating three screens at once at the end of the build.

## Description
Applies the D22 criterion in the D28 ratchet form. Builds the axe-core plus keyboard-traversal harness over a customer-facing screen registry, registers and remediates the Apply screen, and fails closed on an unregistered customer-facing screen. Track (E8-S1) and Repay (E13-S1) then register with this harness as they land, so the three screens NFR-10 names are each covered by the story that introduces them rather than by one terminal remediation pass.

## Scope
**In:** axe-core scan and keyboard-traversal harness wired into the frontend test suite; Customer-facing screen registry the harness enumerates, with a completeness assertion; Registration and accessibility remediation of the Apply screen
**Out:** must not change the behavior or contract of a registered screen endpoint; must not introduce a native or responsive mobile client shell; must not suppress an axe rule to reach a zero-violation count; must not defer a later screen conformance check to a follow-up remediation story

## Acceptance Criteria
- **E17-S1-AC1** — *Given* the customer-facing screen registry, *when* the automated axe-core scan runs against every registered screen, *then* it reports 0 WCAG 2.1 AA violations with no rule suppressed, and asserts it covered 100% of registered screens.
- **E17-S1-AC2** — *Given* each registered screen, *when* its primary flow is traversed using the keyboard only, *then* the flow completes, no focus trap is encountered, and every interactive control exposes an accessible name and a visible focus indicator.
- **E17-S1-AC3** — *Given* a route that renders a customer-facing screen and is absent from the registry, *when* the accessibility suite runs, *then* the suite fails, so Apply, Track and Repay are each held to WCAG 2.1 AA by the story that lands them.

### Operations
1. Define the customer-facing screen registry in `frontend/tests/a11y/registry.ts` (new): a typed list of `{ name, route, screen }` entries, seeded with one entry for the Apply screen (`frontend/src/ui/pages/Apply.tsx`, owned by E4-S3); Track (E8-S1) and Repay (E13-S1) each append one row here as they land.
2. Define the axe-core scan and keyboard-traversal driver in `frontend/tests/a11y/harness.ts` (new): a scan function that runs axe-core against a rendered registry entry with zero rules suppressed, and a traversal function that drives that entry's primary flow using the keyboard only, asserting no focus trap and that every interactive control exposes an accessible name and a visible focus indicator.
3. Define `frontend/tests/a11y/screens.spec.ts` (new): iterate every registry entry, run the axe scan and keyboard traversal from `harness.ts` against each, assert 0 WCAG 2.1 AA violations with no suppressed rule and 100% of registered screens covered, and add a completeness assertion that fails the suite when a route rendering a customer-facing screen is absent from the registry; run it first to surface the Apply screen's current violations.
4. Remediate `frontend/src/ui/pages/Apply.tsx` (owned by E4-S3) for accessibility only — labeling, focus order and visible focus indicators needed to pass the scan and keyboard traversal — with no change to its endpoint or contract, per component-map's Modifies note.
5. Re-run `frontend/tests/a11y/screens.spec.ts` to confirm it passes against the registered and remediated Apply screen, covering AC1 (0 violations, 100% of registered screens covered, no suppressed rule), AC2 (complete keyboard-only traversal with no focus trap and every control accessibly named with a visible focus indicator) and AC3 (the suite fails when a customer-facing route is left unregistered).
