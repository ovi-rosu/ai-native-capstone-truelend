## User Story
As an auditor, I want approved policy versions and every migration to be append-only so that the rules a past decision was made under can always be reconstructed.

## Business Value
Guarantees a decision's basis is reconstructible years later, which is what lets the policy editor ship without an audit objection.

## Description
Implements the D5 immutable side of the line: a policy_version repository with no update or delete method, an architecture test that counts UPDATE, DELETE and ORM mutations against that table across src/ and migrations/, and a migration lint that rejects destructive statements. Mutable loan state stays out of scope by design.

## Scope
**In:** policy_version table and append-only repository; Architecture test counting mutations against policy_version; Migration lint over every file in migrations/, including policy migrations
**Out:** must not expose an update or delete method on the policy_version repository; must not restrict application.status, loan.outstanding_principal or loan.delinquency_bucket, which stay mutable per D5; must not add a destructive statement to any migration to simplify a schema change

## Acceptance Criteria
- **E3-S1-AC1** — *Given* the policy_version repository interface, *when* its public methods are enumerated, *then* no update method and no delete method is exposed.
- **E3-S1-AC2** — *Given* the contents of src/ and migrations/, *when* the immutability architecture test scans them, *then* it reports 0 UPDATE statements, 0 DELETE statements and 0 ORM mutations targeting policy_version.
- **E3-S1-AC3** — *Given* every file under migrations/, *when* the migration lint parses them, *then* it reports 0 DROP TABLE, 0 DROP COLUMN and 0 destructive ALTER statements.
- **E3-S1-AC4** — *Given* a policy migration file, *when* it is parsed by that same lint, *then* it is held to the identical zero-destructive-statement assertion as a schema migration.
