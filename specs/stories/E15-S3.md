## User Story
As a platform operator, I want the read-heavy endpoints measured against the runtime SLO so that a latency regression is caught before a reviewer meets it.

## Business Value
Catches a latency regression at the story that introduces it rather than in a terminal measurement pass whose only remedy touches every read endpoint.

## Description
Applies the D21 criterion in the D28 ratchet form. Builds the load harness over a read-heavy endpoint registry that must contain GET /products, GET /applications, GET /loans/{id} and GET /dashboard, measures p95 and error rate across every registered endpoint, records the figures in the evaluation report, and fails closed on an unregistered read-heavy endpoint. E7-S1, E13-S1 and E14-S1 register their read surfaces as they land.

## Scope
**In:** Load harness measuring p95 latency and error rate per registered endpoint; Read-heavy endpoint registry with a completeness assertion, seeded with the four endpoints NFR-09 names; Measured figures recorded in the evaluation report
**Out:** must not change any endpoint response contract to improve a measurement; must not call an external load-testing service or hold provider credentials; must not add caching that changes a documented read freshness semantic; must not exclude a registered endpoint from a run to reach the budget

## Acceptance Criteria
- **E15-S3-AC1** — *Given* the read-heavy endpoint registry, which contains GET /products, GET /applications, GET /loans/{id} and GET /dashboard, *when* the load run executes against every registered endpoint, *then* the measured p95 latency is under 500 ms and the error rate is under 1% across all of them.
- **E15-S3-AC2** — *Given* the completed load run, *when* the evaluation report is written, *then* it records the measured p95 and error-rate figures for each registered endpoint.
- **E15-S3-AC3** — *Given* a read-heavy endpoint absent from the registry, *when* the SLO suite runs, *then* the suite fails, so a read surface added later is measured by the story that adds it.

### Operations
1. Define the read-heavy endpoint registry in `backend/tests/slo/registry.py` (new): an ordered list of `(method, path)` entries seeded with `GET /products`, the first read-heavy endpoint, from E2-S1's read surface; later stories (E7-S1, E13-S1, E14-S1) each append one row for `GET /applications`, `GET /loans/{id}` and `GET /dashboard` per `component-map.md`'s shared-registry rule.
2. Define the in-process load driver in `backend/tests/slo/harness.py` (new): an httpx + asyncio driver that, for each entry in `READ_HEAVY_ENDPOINT_REGISTRY`, issues a bounded batch of requests against the running app (from E15-S1's `create_app()`), and measures p95 latency and error rate, returning one result record per endpoint — no external load-testing service, per Scope Out.
3. In `backend/tests/slo/test_read_slo.py` (new) add the SLO assertion test: run `LoadHarness` over every entry in `READ_HEAVY_ENDPOINT_REGISTRY` and assert p95 latency is under `project-manifest.json`'s `observability.slo.p95_ms` (500 ms) and error rate is under `observability.slo.error_rate_pct` (1%) for all of them — covering E15-S3-AC1.
4. In `backend/tests/slo/test_read_slo.py` add a test that runs the harness once and asserts every registered endpoint has a measured p95 and error-rate figure recorded in the run's result, in the shape the evaluation report consumes — covering E15-S3-AC2.
5. In `backend/tests/slo/test_read_slo.py` add the completeness assertion: enumerate every `GET` route on the running `create_app()` app that matches the read-heavy heuristic, and assert each is present in `READ_HEAVY_ENDPOINT_REGISTRY`, failing and naming any route absent from it — covering E15-S3-AC3.
