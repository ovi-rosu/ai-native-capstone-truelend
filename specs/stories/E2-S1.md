## User Story
As a business owner, I want Personal, Vehicle and Education products each bound to their own versioned rule set so that I can launch and tune products without a code change.

## Business Value
Turns product launch into a data change, which is the platform's whole premise.

## Description
Deepens the tracer's shallow list into the real catalog: at least three products, each referencing its own policy version whose income, age, score, tenure and rate thresholds differ from the others. Reads policy_version rows written through the E3-S1 append-only store.

## Scope
**In:** Product entity and GET /products read model; Seeded Personal, Vehicle and Education products with distinct policy versions; Product-to-policy-version binding
**Out:** must not hardcode any threshold value in service or API code; must not add multi-currency or per-currency product variants; must not let two products share one policy version row

## Acceptance Criteria
- **E2-S1-AC1** — *Given* the seeded catalog, *when* GET /products is called, *then* at least 3 products are returned and Personal, Vehicle and Education are among them.
- **E2-S1-AC2** — *Given* the returned product list, *when* each entry is inspected, *then* each carries its own policy version id and no two products reference the same one.
- **E2-S1-AC3** — *Given* the three referenced policy versions, *when* their stored threshold values are compared, *then* the minimum income, age, score, tenure and rate values differ between the three versions.

2. Define `rules_for_version(policy_version_id) -> PolicyRules`, `reason_codes_for_version(policy_version_id) -> list[ReasonCode]`, and `active_policy_version(product_code) -> PolicyVersion` in `backend/src/service/policy/policy_accessor.py` (new) — the pinned-version accessor that is the only published way to read Policy Rules (D-D) — each reading via `PolicyVersionRepository.get`/`get_active` (owned by E3-S1) and parsing the stored JSONB through `PolicyRules.model_validate`.

Define `list_catalog() -> list[LoanProduct]` and `get_product(product_code) -> LoanProduct` in `backend/src/service/policy/catalog.py` (new), joining `ProductRepository` rows (owned by E1-S1) with `policy_accessor.rules_for_version` so each returned product carries its own `active_policy_version_id` and the active version's rate/tenure band, with no threshold value hardcoded in this file.
4. Add migration `backend/migrations/versions/0004_seed_catalog.py` (new): for PERSONAL, VEHICLE and EDUCATION, insert one `policy_version` row per product with distinct `PolicyRules`-shaped thresholds (differing `min_income`, `min_age`/`max_age`, `min_credit_score`, tenure band, and `annual_rate_pct`) through the append-only `policy_version` table (owned by E3-S1), inserting any product row the E1-S1 tracer migration did not already create; then update each product's mutable `active_policy_version_id` projection (D-E) to point at its own newly inserted version, so `UNIQUE(active_policy_version_id)` holds and no two products reference the same version (AC2).
5. Add `backend/tests/integration/test_catalog_binding.py` (new): assert `GET /products` (the route owned by E1-S1, backed by `catalog.list_catalog`) returns at least 3 products including PERSONAL, VEHICLE and EDUCATION (AC1); assert each entry's `active_policy_version_id` is distinct across the list (AC2); and assert the three referenced policy versions' `min_income`, `min_age`, `min_credit_score`, tenure and `annual_rate_pct` values are pairwise different (AC3) — covering AC1-AC3.
