## User Story
As a product owner, I want a thin end-to-end slice from login through a policy-threshold change so that the M1 done-when is demoable before any epic goes deep.

## Business Value
Proves the Types-through-UI seam exists at the first story boundary, so no epic integrates six finished layers late.

## Description
The D8 tracer bullet for M1: a seeded login for each of the three roles, a shallow product list, and an admin threshold edit that produces a new active policy version with no restart. Depth is added behind it by E1-S2, E2-S1, E3-S1 and E3-S2.

## Scope
**In:** Session login for the three seeded roles and a role-specific landing surface; Shallow product list endpoint and screen; Threshold save that writes and activates a new policy version
**Out:** must not implement the full authorization matrix — that is E1-S2; must not implement the full three-product catalog rule sets — that is E2-S1; must not verify applicant PAN or Aadhaar against any external registry

## Acceptance Criteria
- **E1-S1-AC1** — *Given* seeded users for CUSTOMER, UNDERWRITER and ADMIN, *when* each logs in with valid credentials, *then* a session is issued naming exactly one role and that role's landing surface loads.
- **E1-S1-AC2** — *Given* the seeded product catalog, *when* a CUSTOMER requests the product list, *then* at least one product is returned and it carries a policy version id.
- **E1-S1-AC3** — *Given* an ADMIN session and a product with a minimum-income threshold, *when* that threshold is saved with a new value, *then* a new policy version id is returned in the response.
- **E1-S1-AC4** — *Given* the newly saved policy version, *when* the product is read again inside the same running process, *then* the read cites the new policy version id with no process restart.
