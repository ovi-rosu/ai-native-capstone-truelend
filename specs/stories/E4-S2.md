## User Story
As a customer, I want the required-document checklist for the product I chose so that I know exactly what to supply, judged against the rules in force when I applied.

## Business Value
Cuts back-and-forth on missing documents and makes each application's basis reproducible after a policy change.

## Description
Deepens the tracer into real intake: the required-document checklist is derived item for item from the selected product's policy version, and the application stores the policy_version_id resolved at submission. Per D6, a version activated later never changes an in-flight application's basis.

## Scope
**In:** Checklist generation from the product's policy version; Persisted policy_version_id pinned at submission; Checklist item entity with document type and unverified status
**Out:** must not re-resolve an application's policy version after submission; must not verify PAN or Aadhaar against an external registry; must not accept more than one applicant per application

## Acceptance Criteria
- **E4-S2-AC1** — *Given* a selected product with a required-document list on its policy version, *when* an application is submitted against it, *then* the generated checklist matches that policy version's list item for item.
- **E4-S2-AC2** — *Given* a submitted application, *when* it is read back from storage, *then* it is in SUBMITTED state and stores the policy_version_id resolved at submission.
- **E4-S2-AC3** — *Given* a policy version activated after that submission, *when* the application is re-read, *then* its stored policy_version_id and checklist are unchanged.
- **E4-S2-AC4** — *Given* a generated checklist item, *when* it is inspected, *then* it carries its document type and an unverified status.

### Operations
1. Add migration `backend/migrations/versions/0006_checklist_item.py` (new) creating the `checklist_item` table per `specs/design/data-models.md` (`id`, `application_id` FK NOT NULL, `document_type`, `label`, `status` default `PENDING`, `rejection_reason` with the `REJECTED`-requires-reason CHECK constraint, `actioned_by`, `actioned_at`) with indexes `(application_id)` and partial `(status) WHERE status = 'PENDING'`; append the `ChecklistItem` table class as one row to the SQLAlchemy table registry in `backend/src/repository/models.py` (owned by E1-S1; single-row registry append).
2. Define `ChecklistRepository` in `backend/src/repository/origination/checklist_repository.py` (new) with `insert_many(application_id, required_documents)`, `list_for_application(application_id)`, `list_pending()` and `set_verification(document_id, status, rejection_reason, actor)`, over the `checklist_item` table from step 1.
3. Define `generate_checklist(application_id, rules: PolicyRules) -> list[ApplicationDocument]` in `backend/src/service/origination/checklist.py` (new): map `rules.required_documents` (from the pinned `PolicyRules`, owned by E2-S1) item-for-item into checklist rows via `ChecklistRepository.insert_many`, each defaulted to `status="PENDING"` and carrying its `document_type` (AC1, AC4).
4. Modify `backend/src/service/origination/intake.py` (owned by E4-S1) to deepen `submit()`: after `ApplicationRepository.insert` pins `policy_version_id` and `status=SUBMITTED`, call `checklist.generate_checklist(application_id, rules)` from step 3 using the same `PolicyRules` already resolved once via `policy.active_policy_version` at submission — never re-resolved afterward (AC2, AC3) — and return the real `document_checklist` list in place of the `E4-S1` tracer's empty placeholder.
5. Add `backend/tests/integration/test_intake_pinning.py` (new): integration tests submitting against a seeded product/policy version and asserting the generated checklist matches the pinned version's required-document list item for item (AC1), the read-back application is `SUBMITTED` and stores the `policy_version_id` resolved at submission (AC2), a later policy-version activation leaves that stored `policy_version_id` and checklist unchanged (AC3), and each checklist item carries its `document_type` with unverified (`PENDING`) status (AC4) — covering AC1-AC4 (and exercising E4-S1's AC1-AC3 submit→score→decide path end to end).
