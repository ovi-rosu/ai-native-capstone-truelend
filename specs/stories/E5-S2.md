## User Story
As an underwriter, I want each application decided against the policy version it was submitted under, with reason codes drawn from that version, so that the basis of every decision is reconstructible.

## Business Value
Gives every approval and rejection a defensible, versioned rationale, which is what makes the policy editor safe to use in production.

## Description
Evaluates the pinned policy version's rules to return AUTO_APPROVE, AUTO_REJECT or MANUAL_REVIEW with at least one reason code, appending a decision_record per D5. Per D6, a MANUAL_REVIEW re-decision and any later override still cite the version pinned at submission.

## Scope
**In:** Rule evaluation producing the three decision outcomes; Reason codes resolved from the application's pinned policy version; Append-only decision_record with latest-record-wins semantics
**Out:** must not update or delete an existing decision_record row; must not return a reason code absent from the application's pinned policy version; must not re-resolve the policy version at decision time

## Acceptance Criteria
- **E5-S2-AC1** — *Given* a scored application, *when* it is decided, *then* the response carries AUTO_APPROVE, AUTO_REJECT or MANUAL_REVIEW plus at least one reason code.
- **E5-S2-AC2** — *Given* the reason codes on that decision, *when* each is looked up, *then* it exists in the policy version pinned on the application.
- **E5-S2-AC3** — *Given* a decided application, *when* the decision is recorded, *then* a new decision_record row is appended and the application's current decision is its latest record.
- **E5-S2-AC4** — *Given* a MANUAL_REVIEW application re-decided after a newer policy version was activated, *when* its decision is read, *then* the re-decision still cites the policy version pinned at submission.

### Operations
1. Add the Alembic migration `backend/migrations/versions/0007_decision_record.py` (new): create the insert-only `decision_record` table (`id`, `application_id` FK, `policy_version_id` FK, `outcome`, `reason_codes` JSONB NOT NULL with at least 1 item, `comment`, `supersedes_id` FK to itself NULL, `decided_by` FK NULL, `decided_at` NOT NULL) with index `(application_id, decided_at DESC)`; no update or delete path, per D-E and SG-2.
2. Append the `DecisionRecord` table class to the SQLAlchemy table registry in `backend/src/repository/models.py` (single-row append, owned by E1-S1), mapping to the `decision_record` table added in step 1.
3. Define `DecisionRepository` in `backend/src/repository/origination/decision_repository.py` (new) with `insert(decision) -> UnderwritingDecision` (append-only; no update/delete method on the class) and `latest_for_application(application_id) -> UnderwritingDecision | None` ordered by `decided_at DESC`, giving AC3 its latest-record-wins read.
4. Define `evaluate(application_id, actor) -> UnderwritingDecision` in `backend/src/service/origination/decision.py` (new): reads the application's pinned `policy_version_id`, resolves rules and reason codes through `rules_for_version`/`reason_codes_for_version` in `backend/src/service/policy/policy_accessor.py` (owned by E2-S1) — never `active_policy_version` — combines them with the Credit Score from `score()` in `backend/src/service/origination/scoring.py` (owned by E5-S1) to produce `AUTO_APPROVE`, `AUTO_REJECT` or `MANUAL_REVIEW` plus at least one declared reason code (AC1, AC2), and appends the result via `DecisionRepository.insert`.
5. Define `record_manual_decision(application_id, outcome, reason_code, comment, actor) -> UnderwritingDecision` in `backend/src/service/origination/decision.py`: validates the supplied reason code against the reason codes declared by the application's pinned `policy_version_id` (read from stored data, never re-resolved as the active version), so a MANUAL_REVIEW case re-decided after a newer version activates still cites the version pinned at submission (AC4), and appends a new `decision_record` via `DecisionRepository.insert`.
6. Add tests for AC1-AC4 in `backend/tests/unit/test_decision_reason_codes.py` (new): the decision-plus-reason-code response shape, reason-code membership in the pinned policy version, append-only/latest-record-wins behaviour across repeated decisions, and the MANUAL_REVIEW re-decision-after-reactivation scenario.
