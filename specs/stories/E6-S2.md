## User Story
As an underwriter, I want one queue of applications awaiting my action and a review screen for MANUAL_REVIEW cases so that I can decide them with the score, reason codes and document state in front of me.

## Business Value
Concentrates underwriter attention on exactly the applications that need a human, with the evidence already assembled.

## Description
The FR-17 workbench: a queue listing exactly the applications in SUBMITTED or MANUAL_REVIEW state, and a decision-review screen showing a MANUAL_REVIEW case's credit score, decision reason codes and per-document verification state, from which the underwriter records a decision.

## Scope
**In:** Workbench queue filtered to SUBMITTED and MANUAL_REVIEW applications; Decision-review screen showing score, reason codes and document state; Underwriter decision recorded through the decision service
**Out:** must not list applications outside SUBMITTED or MANUAL_REVIEW state in the queue; must not render a native or responsive mobile client shell; must not write a decision by any path other than an appended decision_record

## Acceptance Criteria
- **E6-S2-AC1** — *Given* applications spread across every lifecycle state, *when* the workbench queue is listed, *then* it contains exactly those applications in SUBMITTED or MANUAL_REVIEW state.
- **E6-S2-AC2** — *Given* a MANUAL_REVIEW application, *when* its review screen is opened, *then* the screen shows its credit score, its decision reason codes and the verification state of each checklist document.
- **E6-S2-AC3** — *Given* an underwriter deciding a MANUAL_REVIEW case from the review screen, *when* the decision is saved, *then* the application's latest decision record reflects that decision and the case leaves the queue.

### Operations
1. Define `listWorkbenchQueue(): Promise<LoanApplication[]>` and `saveDecision(applicationId, outcome, reasonCode, comment): Promise<UnderwritingDecision>` in `frontend/src/api/workbench.ts` (new), calling `GET /applications?status=SUBMITTED&status=MANUAL_REVIEW` and `POST /applications/{application_id}/decision` through the shared HTTP client in `frontend/src/api/client.ts` (owned by E1-S1, imported not modified), and reusing the application-detail fetch in `frontend/src/api/applications.ts` (owned by E4-S3, imported not modified) for the full record the review screen needs.
2. Define the presentational `ReasonCodeList` component in `frontend/src/ui/components/ReasonCodeList.tsx` (new), rendering an `UnderwritingDecision.reason_codes` list of `{code, text}` pairs.
3. Define the `Workbench` page in `frontend/src/ui/pages/Workbench.tsx` (new): on mount call `listWorkbenchQueue()` from `frontend/src/api/workbench.ts` and render exactly the applications returned — SUBMITTED or MANUAL_REVIEW state, the plain status filter per D-L (AC1) — each row linking to that application's review screen.
4. Define the `DecisionReview` page in `frontend/src/ui/pages/DecisionReview.tsx` (new): fetch the full application via `frontend/src/api/applications.ts` (owned by E4-S3) and render `credit_score`, the decision's reason codes through `ReasonCodeList`, and each checklist item's `DocumentVerificationStatus` from `document_checklist` (AC2, using the verification state E6-S1 produces); on submit call `saveDecision()` from `frontend/src/api/workbench.ts` and, on success, return to the Workbench so the decided case no longer appears in `listWorkbenchQueue()`'s result (AC3).
5. Append one route entry each for `/workbench` and `/applications/:applicationId/review` to the frontend route registry in `frontend/src/ui/routes.tsx` (single-row appends, owned by E1-S1), gated by the UNDERWRITER role from `frontend/src/config/roles.ts` (owned by E1-S1, imported not modified).
6. This story owns no dedicated test file per its bundle; the Workbench-to-DecisionReview-to-save flow wired in steps 3-4 is exactly what the evaluator's Playwright checks QA-VM-059 through QA-VM-061 (`specs/test_artefacts/test-plan.md`) exercise for AC1, AC2 and AC3 respectively.
