## User Story
As an operations user, I want disbursement to record exactly what was released and from where so that the loan book reconciles without touching a real payment rail.

## Business Value
Gives the loan book a complete, reconcilable disbursement record while keeping the funding source a stub, as the capstone requires.

## Description
Deepens the tracer's disbursement into the FR-08 record: released amount, funding-source identifier, DISBURSED state with the generated schedule attached, and a guard so a second disbursement attempt cannot double-release. The funding source is a stub per SG-2.

## Scope
**In:** Disbursement transition writing released amount and funding-source identifier; Stub funding-source adapter; Idempotence guard against a repeat disbursement
**Out:** must not call a real payment rail or hold live provider credentials; must not produce a signed loan agreement or e-signature artifact; must not disburse a loan without a generated schedule attached

## Acceptance Criteria
- **E10-S1-AC1** — *Given* an approved loan with a generated schedule, *when* it is disbursed, *then* the loan record holds the released amount.
- **E10-S1-AC2** — *Given* that disbursement, *when* the loan is read back, *then* it holds a funding-source identifier and is in DISBURSED state with its schedule attached.
- **E10-S1-AC3** — *Given* the stub funding source, *when* the disbursement executes, *then* no external payment rail is called and no signed agreement artifact is produced.
- **E10-S1-AC4** — *Given* a loan already in DISBURSED state, *when* disbursement is attempted a second time, *then* the attempt is refused and the recorded released amount is unchanged.

1. Define the stub funding-source adapter in `backend/src/service/servicing/funding_source.py` (new): resolves a configured stub identifier (e.g. from `Settings.funding_source_id`, owned by E15-S1) with no external payment-rail call, no live provider credentials, and no signed agreement or e-signature artifact produced.

3. Define `disburse(loan_id, actor) -> Disbursement` in `backend/src/service/servicing/disbursement.py` (new): reads the loan and its attached schedule via `LoanRepository.get` and `ScheduleRepository.get_for_loan` (owned by E9-S2), refusing the call when no schedule is attached; resolves the stub identifier via `funding_source.py`; calls `DisbursementRepository.insert` (owned by E9-S2) to write the released amount, funding-source identifier and the `DISBURSED` transition in one transaction, relying on that repository's migration-level `UNIQUE(loan_id)` constraint as the structural idempotence guard; catches a repeat call and raises `AlreadyDisbursed` so the previously recorded released amount is left unchanged.
4. Modify `backend/src/api/servicing/routes.py` (owned by E9-S2) so `POST /loans/{loan_id}/disbursement` calls `disbursement.disburse` in place of the tracer's inline insert, still guarded by `require_roles(ADMIN)` per D-N.
5. Add the idempotence integration test in `backend/tests/integration/test_disbursement_idempotence.py` (new), covering AC1-AC4: the loan record holds the released amount after disbursement (AC1); reading the loan back shows the funding-source identifier, `DISBURSED` state and the attached schedule (AC2); the stub disbursement calls no external payment rail and produces no signed agreement artifact (AC3); a second disbursement attempt on an already-`DISBURSED` loan is refused with the recorded released amount unchanged (AC4).
