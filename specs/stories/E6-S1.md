## User Story
As an underwriter, I want to work a queue of submitted documents and mark each VERIFIED or REJECTED with a reason so that the applicant knows precisely what to resupply.

## Business Value
Turns document chasing into a worked queue with a recorded reason, cutting repeat rejections.

## Description
The FR-06 verification queue over the checklist items intake generates. Each document transitions to VERIFIED, or to REJECTED with a non-empty reason; actioned documents leave the queue. Runs under the E1-S2 role boundary and is audited as a privileged action.

## Scope
**In:** Verification queue read model over unactioned checklist documents; VERIFIED and REJECTED transitions with a mandatory rejection reason; Queue exclusion of already-actioned documents
**Out:** must not accept a REJECTED transition with an empty reason; must not verify a document against an external registry; must not block schedule generation on document verification, per D9

## Acceptance Criteria
- **E6-S1-AC1** — *Given* a checklist document in the verification queue, *when* an underwriter marks it VERIFIED, *then* its stored status reads VERIFIED.
- **E6-S1-AC2** — *Given* a checklist document in the verification queue, *when* an underwriter marks it REJECTED with a reason, *then* the stored row reads REJECTED and carries that non-empty reason.
- **E6-S1-AC3** — *Given* a document being rejected with an empty reason, *when* the transition is attempted, *then* it is refused and the document's stored status is unchanged.
- **E6-S1-AC4** — *Given* documents that have already been actioned, *when* the verification queue is listed, *then* those documents are absent from the returned queue.

### Operations
1. Define a `DocumentVerificationRequest` Pydantic model in `backend/src/service/origination/document_verification.py` (new) that requires a non-empty, non-whitespace `rejection_reason` whenever `status == REJECTED`, giving AC3 its application-layer half of the double enforcement (the database CHECK constraint on `checklist_item` already exists, owned by E4-S2).
2. Define `verification_queue() -> list[ApplicationDocument]` in `backend/src/service/origination/document_verification.py`, delegating to `ChecklistRepository.list_pending()` in `backend/src/repository/origination/checklist_repository.py` (owned by E4-S2, imported not modified) so already-actioned documents are excluded (AC4).
3. Define `verify_document(application_id, document_id, status, rejection_reason, actor) -> ApplicationDocument` in `backend/src/service/origination/document_verification.py`: validates the request through `DocumentVerificationRequest`, then calls `ChecklistRepository.set_verification(...)` (owned by E4-S2, imported not modified) to persist the VERIFIED or REJECTED transition (AC1, AC2), and records an `AuditEntry` via `audit(...)` in `backend/src/service/identity/audit.py` (owned by E1-S2).
4. Define `GET /documents/queue` and `POST /applications/{application_id}/documents/{document_id}/verification` in `backend/src/api/origination/document_routes.py` (new), both guarded by `require_roles(UNDERWRITER)` from `backend/src/api/deps.py` (owned by E1-S1); the verification route returns a 422 and leaves the document's stored status unchanged when `DocumentVerificationRequest` rejects an empty reason (AC3).
5. Append the `include_router(document_routes.router)` call to the app factory router registry in `backend/src/api/app.py` (single-row append, owned by E15-S1).
6. Add integration tests for AC1-AC4 in `backend/tests/integration/test_document_queue.py` (new): a VERIFIED transition, a REJECTED-with-reason transition, an empty-reason rejection attempt that leaves the stored status unchanged, and queue exclusion of already-actioned documents.
